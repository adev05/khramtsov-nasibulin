# Когда автоматическая проверка находит ошибку

Оба эксперимента проведены 19 ноября 2026 года в ветке `coursework` [учебного форка](https://github.com/adev05/khramtsov-nasibulin/tree/coursework). За основу взят [коммит `6fc15f1`](https://github.com/devops-praktik-2026/khramtsov-nasibulin/tree/6fc15f1b1155c3f9003c17b854366398d31e7941). В исходном репозитории Ruff присутствовал с первого коммита. Для опыта подготовлена ветка, в которой автоматическая проверка включена отдельным коммитом.

Локальная среда — macOS 27.2 (arm64), Python 3.12.14, pre-commit 4.3.0 и pytest 9.2.0. На GitHub Actions использовался образ `ubuntu-latest` с Python 3.12. [Версии и команды](../results/environment.txt).

## 1. Какие замечания находит Ruff

Использована одна версия Ruff, `0.14.4`, с правилами проекта из [ruff.toml](../ruff.toml). Команда `ruff check --output-format concise .` проверяла весь репозиторий. На исходном коде она завершилась с нулём замечаний. Затем в `services/orders/orders/api.py` и `services/orders/orders/accounts_client.py` добавили по неиспользуемому импорту, нарушили порядок импортов и добавили по комментарию длиннее 100 символов.

| Замечание | Исходный код | Подготовленное состояние «до» | После исправлений |
| --- | ---: | ---: | ---: |
| `F401` — неиспользуемый импорт | 0 | 2 | 0 |
| `I001` — порядок импортов | 0 | 2 | 0 |
| `E501` — длинная строка | 0 | 2 | 0 |
| **Всего** | **0** | **6** | **0** |

В подготовленном состоянии сначала выполнили разовую локальную проверку, затем включили ту же команду в GitHub Actions. Во всех шести сообщениях совпали файл, позиция и правило. [Снимок «до»](https://github.com/adev05/khramtsov-nasibulin/tree/experiment-before) · [Локальный отчёт](../results/before.txt) · [Запуск CI](https://github.com/adev05/khramtsov-nasibulin/actions/runs/44425749915).

Исправление набора заняло **12,959 с**. Замер начался при записи первой явной правки в `accounts_client.py` и закончился при возврате успешного локального `ruff check` после правки `api.py`. Автоматизированный исполнитель внёс две явные текстовые правки с выключенным автоисправлением Ruff. Замер характеризует этот способ редактирования. Чтобы получить показатель для человека, тот же набор можно исправить вручную от метки `experiment-before` с секундомером. После исправлений файлы приложения побайтово совпали с исходными, проверка CI также прошла. [Метки времени](../results/repair.txt) · [Снимок «после»](https://github.com/adev05/khramtsov-nasibulin/tree/experiment-after) · [Запуск CI](https://github.com/adev05/khramtsov-nasibulin/actions/runs/44425867785).

### Ошибки в поведении приложения

Каждую правку внесли отдельно. До правки и после её отмены соответствующий тест проходил. При каждой из трёх правок `ruff check .` завершился успешно. Проверка результата запроса существующими тестами дала следующие различия.

| Временное изменение | Ожидаемый результат | Результат теста с ошибкой |
| --- | --- | --- |
| Удалён фильтр по клиенту в списке заказов | Клиент 7 получает заказы 10, 30 и 40 | В ответ попал также заказ 20 другого клиента. [Журнал](../results/logic-filter.txt) |
| Для количества товара разрешён ноль | Ответ 422 для заказа с нулевым количеством | Сервис создал заказ и вернул 201. [Журнал](../results/logic-quantity.txt) |
| Для создания заказа выставлен статус 200 | Успешное создание возвращает 201 | API вернул 200 при обоих проверенных количествах. [Журнал](../results/logic-status-code.txt) |

В этом опыте правила Ruff выявили нарушения в оформлении и использовании импортов. Ошибки в фильтрации, границе допустимого значения и коде ответа выявили тесты, в которых записаны требования к сервису. После восстановления полный набор из 67 тестов проходит. [Полный запуск](../results/make-test-restored.txt).

## 2. Время до сообщения об ошибке

Для каждого повтора использовали один и тот же чистый `services/orders/orders/api.py`. На третью строку вставляли `import os` и пустую строку. Такая правка вызывает одно замечание `F401`. Другие анализаторы и автоисправления выключены. При проверке хука диагностика редактора выключена. При замере CI выключены обе локальные проверки. Хук был установлен до измерений.

Начало каждого замера — первый кадр с полностью вставленным импортом. Конец — первый кадр, на котором видна диагностика Ruff с кодом `F401`. Обе отметки берутся с одной записи. В таблице приведена разность номеров кадров, делённая на частоту видео.

В VS Code 1.146.0 была раскрыта панель Problems. Официальное расширение Ruff 2026.96.0 использовало Ruff 0.14.4. Для пяти записей окна сохранены отметки исходных кадров, видео приведено к 60 кадрам/с. Для измеренного интервала в этом опыте оценка погрешности захвата составляет до ±0,06 с. Один дубль с пропуском кадров перед вставкой был переснят.

При опытах с хуком и CI изолированное окно наблюдения показывало изменяемый файл и вывод команд. После вставки последовательно выполнялись сохранение, `git add` и `git commit`. Хук пять раз остановил коммит с кодом 1. Для CI хук отключали и выполняли также `git push`. Команды запускались программно. Частота записи окна — 25 кадров/с, шаг видеошкалы — 0,04 с. Максимальное расхождение с интервалом между событиями вставки и показа в самом окне составило 0,035 с для хука и 0,407 с для CI.

Журнал GitHub Actions запрашивался через API для конкретных коммита и задания. Конец замера CI — первое отображение полученной строки Ruff в окне наблюдения. В это время входят публикация журнала и опрос API. Отметка первого появления ошибки в веб-интерфейсе GitHub в ходе выполнения отдельно не измерялась. По меткам UTC от вставки до записи F401 на самом сервере в пяти запусках прошло приблизительно 13, 11, 11, 12, 11 с соответственно (медиана около 11 с). Для этой оценки использованы часы клиента и сервера. Относительный сдвиг часов конкретного сервера и клиента неизвестен, поэтому оценки округлены до секунд.

В этой серии редактор первым показывал ошибку. Хук обнаруживал её при попытке коммита, а в CI приходилось ждать отправки кода, запуска задания и появления его вывода. Эти интервалы описывают получение обратной связи в условиях опыта.

## Как повторить

Выполнить команды из корня ветки `coursework` на macOS или Linux с установленными Python 3.12 и Make.

```sh
make setup PY=python3.12
.venv/bin/python -m pip install pre-commit==4.3.0
.venv/bin/pre-commit install --install-hooks
.venv/bin/ruff --version
.venv/bin/ruff check .
make test
```

После создания окружения открыть корень клона как доверенную папку VS Code с расширением `charliermarsh.ruff`. В Output → Ruff проверить выбор бинарника из `.venv` и версию 0.14.4. Для опыта раскрыть панель Problems. Для опыта с хуком отключить в редакторе диагностику, вставить правку, сохранить, добавить файл в индекс и попытаться выполнить коммит. Для CI сначала отключить локальный хук командой `.venv/bin/pre-commit uninstall`, выполнить ту же правку и отправить коммит в ветку `coursework` своего форка с включёнными Actions. Между повторами возвращать файл к чистой версии. Для проверки первого опыта с полным набором правил использовать теги `experiment-before` и `experiment-after` и команду `.venv/bin/ruff check .`.
